# Ozon 供应商 SKU 决策界面设计

## 背景与根因

当前采集审核把 1688 的底层 SKU 数据直接交给用户：

- 页面没有可选规格时，内容脚本本来可以构造“页面唯一 SKU”，但 `hasVisibleVariantSelector()` 用 `[class*='sku'] button` 等宽泛选择器判断页面是否存在规格。页面中的无关按钮也会命中，导致兜底被跳过，最终保存空 `sku_options`。
- 工作台只按 `sku_options.length` 判断是否可确认。空数组一律显示“未采集”，确认按钮禁用，没有识别 `sku.evidence=no_visible_variant_selector` 这种真实的唯一 SKU 证据。
- 多 SKU 时，工作台平铺 `raw_label`、套装数量、原始价格和库存，没有在选择区展示 Ozon 原商品目标规格，也没有归纳候选差异或推荐置信度。用户只能阅读一组缺少语境的底层组合。

这三个现象来自同一个错误模型：系统把“采集数据结构”当成了“用户决策界面”，同时把“没有规格选择器”和“规格采集失败”混成同一状态。

## 目标

1. 页面确实没有可选规格时，显示一个有页面证据的唯一 SKU，并允许用户明确确认。
2. 页面存在多个真实 SKU 时，先展示 Ozon 原商品目标规格，再按中文字段展示每个 1688 候选的数量、尺寸、颜色、套装、价格和库存。
3. 系统只在一个候选具有唯一且明确的确定性字段重合时标记“建议选择”；证据不足或多个候选同分时不默认选择。
4. 原始字段继续保留在证据详情中，但不再作为主要决策界面。
5. 用户仍然必须点击确认；不得自动锁定、伪造 SKU、触发采购、生图、上传、发布或审批。

## 方案

### 唯一 SKU 归一化

内容脚本以已经解析出的 `sku_groups` 为准。只有真实规格组非空时才阻止唯一 SKU 兜底；不得再用页面任意 class 名中包含 `sku` 的按钮推断存在规格。

为了兼容已经采集的空矩阵，服务端增加同一套只读归一化：当且仅当以下条件同时满足时生成一个候选：

- `sku_options` 为空；
- `sku_groups` 为空；
- `sku.evidence` 明确为 `no_visible_variant_selector`，或可见标签明确写明“单一 SKU（页面无可选规格）”；
- 页面已有 `offer_id`、可解析价格和至少一张供应商图片。

候选使用真实 `offer_id` 作为稳定 ID，证据来源为 `single_sku_detail_page`，库存状态记为 `unknown`，不推断页面没有提供的数据。若标题或属性明确包含“3件、4支”等套装数量，可用严格单位表达式提取；否则数量为 1。

确认接口、选择收据完整性校验和审核接口必须调用同一归一化函数，避免界面能看到但后端不能确认，或确认后被完整性校验判坏。

### 多 SKU 决策

工作台决策区分为两层：

1. `Ozon 原商品目标`：把 Ozon `target_sku.selected_options` 按数量、尺寸、颜色、套装/型号等常见语义显示；无法识别的字段保留原名。
2. `1688 可采购规格`：每张卡片优先显示结构化 `selected_options`，其次才显示 `raw_label`；同时显示套装数量、价格、库存。

确定性比较只使用选项字段中的明确文本和数字信息，不做跨语言语义猜测：

- 完全相同的规范化值属于强匹配；
- 唯一的明确数字/尺寸重合可以作为辅助匹配；
- 只有一个候选的得分达到门槛且严格高于第二名时才标记“建议选择”；
- 没有唯一高置信候选时不预选，并明确提示用户系统没有找到可证明的唯一对应项。

卡片点击后才允许“确认所选 SKU”。唯一 SKU 模式自动选中唯一候选，但仍需用户点击“确认页面唯一 SKU”。

## 状态与错误边界

- `single`：一个真实候选，页面无规格选择器；自动选中但不自动确认。
- `multiple_recommended`：多个候选，一个候选有唯一高置信证据；标记并预选建议项，用户仍需确认。
- `multiple_ambiguous`：多个候选，没有唯一高置信证据；不预选。
- `matrix_missing`：存在规格组但没有完整真实 SKU 组合，继续显示采集不完整门禁，不制造候选。

## 验证

- Node VM 测试证明无规格页即使存在误命中的 `sku` class 按钮，也回传一个完整唯一 SKU。
- 服务测试证明旧的空矩阵加 `no_visible_variant_selector` 证据会暴露一个可确认候选，确认后收据校验仍完整。
- 服务测试证明存在真实规格组但矩阵为空时不会生成唯一 SKU。
- 页面合约测试证明决策区包含 Ozon 目标、结构化候选、建议/歧义提示和两个上下文按钮文案。
- 聚焦测试、浏览器 Node 合约和完整 pytest 全部通过。

全部验证使用本地夹具和临时运行目录，不触发真实采集、生图、上传、发布或最终审批。

## 多 SKU 候选收敛补充

平铺全部真实 SKU 仍然会把判断成本转嫁给用户，尤其是 1688 将容量、造型和材质等级塞进同一个“颜色/规格”值时。决策区因此改为目标驱动的渐进展示：

1. 比较输入同时读取 Ozon 标题、已选属性和公开属性，不再只读 `selected_options`。
2. 对 `25/50 ml`、`25/50ml`、`300x10x5 mm` 等明确度量做规范化；成对容量会展开为两个可比较事实，俄文和英文单位归一到同一单位。
3. 首屏只展示与 Ozon 明确度量重合的真实 SKU；无法证明的其余 SKU 放入“查看其他规格”折叠区。
4. 多个候选同分时不预选。例如 Ozon 明确 `25/50 ml` 时，只展示对应的 201/304 候选，由用户判断剩余材质或造型差异。
5. 每个候选显示采集到的 SKU 绑定图、价格和库存，避免只凭长文本判断。
6. 已锁定但与当前目标不一致的 SKU 单独显示，原不可变收据不被静默覆盖。

该规则基于通用度量事实和采集证据，不针对某一个商品名称写死 SKU。

## 已锁定 SKU 的可审计重选

用户可能在锁定 SKU 或主体证据后发现选错。原有不可变收据不能直接覆盖，但也不能让用户卡在错误决定上。因此提供“重新选择 SKU”，并遵守以下边界：

1. 是否允许重选只由该商品图片任务是否开工决定，不由批次整体阶段猜测。最后一件商品确认后批次可能已进入图片阶段，但只要该任务仍为 `pending` 且没有生成尝试，仍可重选。
2. 队列以单个 SQLite 事务原子检查任务状态和尝试记录，只停止尚未开工的任务。已被 worker 领取或已有尝试记录时拒绝重选。
3. 旧 SKU 收据写入 `supplier_sku_selections.json.history`，旧主体证据和图片任务 ID 写入 `subject_masters.json.history`；活动记录才从 `selections/items` 移除。
4. 重选后用户回到同一套目标收窄候选界面。即使批次已处于图片阶段，也可重新确认 SKU 和主体，不需要篡改批次状态。
5. 操作写入 `supplier_sku_selection.reopened` 运行事件。工具台不会自动执行重选；只在用户点击并二次确认后变更当前记录。
