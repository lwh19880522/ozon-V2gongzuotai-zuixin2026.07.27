# Ozon 浏览器采集人工恢复设计

日期：2026-07-20

状态：用户已确认设计，规格已自审，等待用户复核

## 目标

保留 Ozon V2 现有自动流程，同时为两类浏览器采集增加明确、可恢复的人工入口：

1. Ozon 原商品及其页面原始属性字段采集失败、中断或被用户关页后，可从批次首页重新启动。
2. 1688 受管采集失败、中断或被用户关页后，可从采集审核页重新启动。

人工恢复只能继续当前批次未完成的商品，不得重新采集已经成功的商品，不得重置批次、覆盖成功证据或绕过现有最终验收。

## 已确认范围

本设计中的“字段回传”是 Ozon 原商品采集结果里的页面原始属性字段，不是：

- Ozon 类目属性模板采集；
- AI 字段优化或内容生成；
- Yandex 式 Codex 字段任务队列；
- Seller API 最终字段写回。

本次只修改 Ozon V2。Yandex 设计用于参考交互与恢复原则，不修改 Yandex 代码或运行数据。

## 当前缺口

现有扩展对一般内容脚本错误会自动尝试再次派发，工作台也有全局“继续自动执行”。但仍存在三类人工恢复缺口：

- 用户主动关闭受管标签页后，系统正确保持停止，却没有对应阶段的显式恢复按钮。
- 某些卡住或旧派发令牌状态不会通过全局“继续自动执行”产生新的浏览器派发令牌。
- Ozon 采集中间结果主要保存在标签页会话状态；若标签页已关闭，单纯刷新派发令牌无法可靠跳过已成功商品。

1688 受管采集已经逐件写入 `supplier_selection_draft.json`，活动任务也会过滤已采集商品，因此已有安全的未完成通道恢复基础。

## 方案选择

采用阶段专用恢复按钮，共用一套受限的后端重新派发逻辑。

未采用以下方案：

- 仅在首页提供通用“重新启动当前浏览器任务”：用户无法判断当前重启的是 Ozon 还是 1688，且审核页仍没有就地恢复入口。
- 重置整个采集阶段：会重复采集成功商品，存在覆盖证据和制造重复结果的风险。

## 界面设计

### 批次首页

当当前批次处于 `ozon_collecting` 且尚无正式 Ozon 采集结果时，在 Ozon 采集阶段显示：

`重新启动 Ozon 原商品采集`

按钮说明明确表示：已完成商品及其原始属性字段不会重复采集。

### 采集审核页

当批次处于 `supplier_review` 或 `supplier_collecting` 且供应商采集尚未完成时，在“五通道采集”操作区显示：

`重新启动 1688 采集`

按钮说明明确表示：只重新打开未完成通道，已经回传的 1688 商品保持终态。

### 按钮状态

- 请求提交期间立即禁用，避免连续双击。
- 阶段完成后显示对应“采集已完成”状态并禁用。
- 请求失败时恢复可用状态并显示后端返回的中文错误。
- 扩展离线时，恢复请求可以保存为待派发；界面显示等待扩展上线，不宣称采集已启动。

## 后端重新派发合同

新增一个批次范围的恢复入口：

`POST /api/batches/{run_id}/browser-task/restart`

客户端不提交任意任务类型。后端从当前批次状态推导唯一允许恢复的任务：

- `ozon_collecting` -> `ozon_collection`
- `supplier_review` -> `supplier_selection`
- `supplier_collecting` -> `supplier_collection`

其他状态全部拒绝。完成态、正式结果已存在或批次不匹配时也必须拒绝。

合法恢复请求执行以下动作：

1. 保留批次状态、冻结商品、合同文件、检查点和正式结果。
2. 清除当前批次的浏览器任务取消标记。
3. 写入新的 `browser_task_resumed_at`，作为新的 `dispatch_token`。
4. 记录 `browser_task.user_restart_requested` 事件，包含任务类型、已完成数量和待处理数量。
5. 返回结构化结果，说明任务已重新派发或正在等待扩展上线。

恢复入口不得直接打开浏览器、直接采集页面或伪造成功；真实浏览器动作仍由现有扩展在领取新令牌后执行。

## Ozon 采集检查点

### 文件

新增当前批次文件：

`ozon_collection_draft.json`

不新增数据库表。检查点只保存已经通过单件基础校验的 Ozon 候选及其页面原始属性字段。

### 写入时机

扩展每成功完成一件 Ozon 商品后，向批次进度入口提交该候选。服务端验证后以冻结商品顺序、按 `seed_id` 唯一写入检查点。

固定入口：

`POST /api/batches/{run_id}/ozon-collection-progress`

检查点至少包含：

- `schema_version`
- `run_id`
- 有序 `ozon_candidates`
- `updated_at`

候选继续使用现有 Ozon 采集结构，不创建第二套商品模型。

### 验证规则

- `run_id` 必须是当前批次。
- 批次必须仍处于 `ozon_collecting`。
- `seed_id` 必须属于当前冻结合同，且每个 seed 只能有一个成功候选。
- 商品 ID 必须唯一且不能在排除列表中。
- 候选必须通过现有 Ozon 公共证据基础字段校验；原始属性字段随候选一起保存。
- 客户端提交顺序不能覆盖服务端冻结顺序。

### 恢复规则

活动 Ozon 浏览器任务向扩展提供已验证检查点。扩展按合同顺序重建状态：

1. 保留仍与当前 seed、商品 ID 和排除规则一致的成功候选。
2. 从第一件未完成 seed 开始继续。
3. 不合并其他批次、其他任务类型或不匹配合同的会话状态。
4. 不把检查点当成正式完成结果。

最终 `ozon_collection_result.json` 仍由现有完整批次验收生成。检查点保留作续跑与诊断证据。

## 1688 恢复规则

1688 不新增检查点模型：

- `supplier_selection_draft.json` 继续逐件保存用户确认并回传的供应商商品。
- `supplier_review` 的活动任务继续过滤已经捕获的 `seed_id`，新令牌只包含未完成通道。
- `supplier_collecting` 继续复用现有合同和本地采集游标。
- 已终态通道不得因恢复令牌改变而重新打开。

## 用户关页和重复请求

- 用户关闭受管标签页后，旧派发令牌继续保持停止，不允许后台轮询强制重开。
- 用户点击对应恢复按钮后，新令牌只允许重新打开一次。
- 后台继续使用批次和任务类型组成的任务键，避免同一令牌创建重复标签页或窗口。
- 前端禁用提交中的按钮；后端仍需保证重复请求不会清空检查点或产生重复成功记录。

## 错误处理

- 检查点损坏或与合同不一致：拒绝恢复，保留原文件并返回明确诊断，不静默从头覆盖。
- 正式结果已经存在：返回阶段已完成，不产生新令牌。
- 扩展离线或版本不匹配：保存待派发状态并返回等待原因，不伪装为已打开页面。
- 批次状态在用户点击前已经推进：按最新状态拒绝陈旧页面请求。
- 单件检查点提交失败：扩展保留当前页面状态并重试检查点写入，不把未持久化候选计为可安全跳过。

## 测试策略

遵循测试先行，全部使用本地假数据，不访问真实 Ozon 或 1688。

### Python

- 首页在 `ozon_collecting` 显示 Ozon 恢复按钮，并在其他阶段隐藏或禁用。
- 采集审核页在 `supplier_review` / `supplier_collecting` 显示 1688 恢复按钮，完成后禁用。
- 恢复 API 只接受三种映射状态，拒绝完成态和不相关阶段。
- 合法恢复刷新派发令牌、清除取消标记并记录事件，但不改变批次状态或合同。
- Ozon 检查点按合同顺序保存、去重、拒绝跨批次或非法候选。
- 正式结果生成后检查点不能再次触发恢复。

### Node

- 新 Ozon 派发令牌从服务端检查点恢复已完成候选，从第一件未完成 seed 继续。
- 合同或商品 ID 不匹配时不合并陈旧状态。
- 1688 新令牌只创建未完成通道。
- 用户关页后旧令牌不重开；显式恢复的新令牌只重开一次。
- 连续点击和重复轮询不会创建重复标签页或重复提交成功候选。

### 完整验证

运行：

`python -m pytest -q`

测试不得触发真实采集、生图、上传、发布或最终审批。

## 验收标准

- 现有自动 Ozon 与 1688 流程保持不变。
- Ozon 采集未完成时，批次首页始终有明确恢复入口。
- 1688 采集未完成时，采集审核页始终有明确恢复入口。
- Ozon 恢复跳过已持久化的成功商品，并保留其原始属性字段。
- 1688 恢复只打开未完成通道。
- 用户关页后不会被旧令牌强制弹回；点击恢复后只重新打开一次。
- 完成态、跨批次和不匹配合同的恢复请求被拒绝。
- 全量自动测试通过，且验证过程没有真实业务动作。

- 不增加 Ozon 类目模板人工重启按钮。
- 不重构现有批次状态机，不新增数据库表。
