# Ozon V2 Architecture Contract v0.1

This file is the binding architecture contract for Ozon V2 work in this
workspace.

The repository root is the implementation root:

```text
<repository-root>
```

The directory name `ozon-v2-ops-controller/` in the original design is the V2
code-root shape. Do not treat a parent-level directory with a similar name as
the implementation root.

## Guiding Rule

V2 must not continue the old pattern of "build a pile first, rescue it later".
Every step must follow this contract. Do not add temporary capability that
bypasses the layers below.

## FastMCP Principles

- `FastMCP server` is a container for tools, resources, and prompts. It owns
  protocol wiring and lifecycle only. It must not carry business logic.
- `tools` are executable entry points. They must stay thin and must not grow
  long business flows.
- `resources` are read-only data exposers, such as status, artifacts, and config
  snapshots.
- `lifespan` is for startup/shutdown initialization and cleanup, such as a
  singleton guard, path initialization, and log context.
- `Context` is for request-level logging, progress, and context access. Do not
  pass state through global variables.

## Layer Contract

```text
FastMCP Layer
  Only registers tools/resources/lifespan. Does not write business flows.

Application Layer
  Orchestrates use cases: doctor, start, next, ingest, status.

Domain Layer
  Holds pure business rules: state machine, dedupe rules, field validation,
  candidate judgment.

Adapter Layer
  Handles external IO: file system, Seller API, approved browser task
  contracts.

Runtime Data
  The sibling directory <repository-parent>\OzonOpsV2 stores runtime data only.
  It must not contain business code or be committed to this repository.
```

## Non-Negotiable Boundaries

1. `mcp/server.py` only declares and registers FastMCP objects. It must not
   contain business process code.
2. Tool functions must not directly write complex business logic. A tool may
   call at most one service.
3. State transitions must live in `domain/state_machine.py`. They must not be
   scattered across tool functions.
4. Browser automation must not be embedded into this controller. V2 only
   generates collection task contracts. Codex may use an approved browser worker
   (`mcp__playwright_mcp` or the Codex in-app browser), then writes the result
   back through `ozon_v2_ingest_*`.
5. Runtime state must be generated by tools. Starting the MCP process must not
   lose state.
6. The singleton guard belongs in FastMCP `lifespan`. Do not rely on the user to
   restart manually.
7. Do not import or share legacy plugin state, runtime roots, or old `run_id`
   values.

## Phase One Scope

Do not build upload tasks, images, or a ready pool in phase one.

Phase one only includes:

- `ozon_v2_doctor`
- `ozon_v2_status`
- `ozon_v2_start_run`
- `ozon_v2_next`
- `ozon_v2_ingest_collection_output`
- FastMCP `lifespan` singleton guard

The collection loop must first support:

```text
Seller uploaded dedupe
Generate Ozon public collection task
Generate 1688 supplier collection task
Validate approved browser worker output
Generate evidence CSV
```

## Execution Rules

Before each implementation step, state:

- Which layer the step belongs to: FastMCP, Application, Domain, or Adapter.
- Which files will be created or modified.
- What the step will not do.
- How completion will be tested.

Additional rules:

- Do not implement many things at once.
- Do not place "capability" before the correct structure.
- Do not add old-plugin adapters, old conditions, or legacy compatibility paths.
- Keep runtime data separate from business code.
- Keep V2 independent from old plugin state and identifiers.
